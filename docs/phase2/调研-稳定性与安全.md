## 1 · DNS 失败处理（P3 根治方案）

**现状**：校验期 DNS 失败（`UnknownHostException`）在 `security/UrlSecurityValidatorImpl.kt:129-149`（resolveHost 捕获后返回 null）→ `:113-120` 统一报 `Security(INVALID_HOST, "主机解析失败或非法")`；而建连期 DNS 失败经 `security/SecureHttpClientImpl.kt:379-381` 映射为 `Network(DNS_FAILURE)`。同一"DNS 不可达"在两条路径语义分裂：UI 文案一为"主机名无效（修改网址）"、一为"无法访问（重试）"，且 `presentation/reader/ReaderViewModel.kt:600-606` 判 `Security` 不可重试 → 断网时校验路径先失败，用户被引导"修改网址"（验收单 L2 幕断网口径依赖 OFFLINE 分支，DNS 先行失败时口径不一致）。
**差距**：`INVALID_HOST` 同时承载"主机格式非法"与"解析不出"两个语义；错误族归属错位。
**建议方案**（与 fail-closed 兼容）：
1. `BlockedReason` 增列 `DNS_UNAVAILABLE`（契约 02 §4.1 变更，需批准）：resolveHost 将 `UnknownHostException`（含空解析结果）与"语法/IDN 解析失败"分流，前者报 `DNS_UNAVAILABLE`，后者维持 `INVALID_HOST`。
2. `SecureHttpClientImpl.doFetch` 收到 `Blocked(DNS_UNAVAILABLE)` 时返回 `ReaderError.Network(DNS_FAILURE, …)` 而非 `ReaderError.Security`——**请求仍未发出、黑名单未豁免**，fail-closed 不变，仅错误族归位网络侧，用户获得"重试"语义。
3. SSRF 边界：黑名单命中（LOOPBACK/PRIVATE/…）一律维持 Security 族；`DNS_UNAVAILABLE` 仅在"一个地址都未解析到"时出现，不存在"解析失败即放行"的通路。
4. UI 侧零改动（DNS_FAILURE 文案与重试恢复已在 02 §10 与 `ui/components/ErrorText.kt`）。
**影响文件**：security/UrlSecurityValidator.kt、security/UrlSecurityValidatorImpl.kt:113-120、security/SecureHttpClientImpl.kt:110-120、docs/02-接口契约.md §4.1/§10；补 validator+client 映射单测各 1-2 例。
**风险**：低。纯错误分类调整，不触碰黑名单判定；QA L 幕断言口径需同步。
**工作量**：S。

## 2 · 网络异常恢复（自动重试与退避）

**现状**：错误即数据（AppResult，契约 §4.2）；重试全部手动（ReaderViewModel.retryLoad:217、ImportViewModel.retry:109、CatalogScreen.kt:182）；仅进度保存有一次 200ms 重试（ReaderViewModel:555-563）；`SecureHttpClientImpl.kt:88` 显式 `retryOnConnectionFailure=false`（防静默重试绕过限流与逐跳校验，不可推翻）。`NetworkFailure.RATE_LIMITED`（domain/error/ReaderError.kt:48）与文案（ErrorText.kt:47）**存在但全仓无生产者**——HTTP 429 落 `readAndBuild` 的 `code>=400`（SecureHttpClientImpl:225-227）报 HTTP_ERROR_STATUS。
**差距**：无幂等 GET 自动重试/指数退避；无 Retry-After 处理；批量缓存单章失败即计入失败继续（ContentCacheManagerImpl:106-109），断网整批全败无恢复。
**建议**（最小接入层设计）：
1. 重试层放 **parser 管线**（ParserPipelineImpl 内 fetch 包装），不放客户端内：请求预算（ParseOptions.maxTotalRequests=30，parser/core/ParseOptions.kt）计数在管线侧，重试计入预算才不破坏契约 §5.2；客户端内重试会使预算对重试透明膨胀。
2. 可重试集合：DNS_FAILURE/CONNECT_TIMEOUT/READ_TIMEOUT/CONNECTION_REFUSED/EMPTY_RESPONSE；不可重试：TLS_ERROR、HTTP_ERROR_STATUS、RESPONSE_TOO_LARGE、REDIRECT_LOOP、TOO_MANY_REDIRECTS、Security.\*、Parse.\*。指数退避 1s/2s/4s±抖动，默认重试 2 次，delay 挂起点天然可取消。
3. 429（可选 503）映射为 RATE_LIMITED 并透出 Retry-After（ReaderError 增字段，契约变更回路）；管线按其等待重试，并联动 §3 的 host 级临时间隔加倍。
4. 批量缓存二期 Worker 化（data/work/ChapterDownloadWorker.kt 骨架已备）：批尾对可重试失败章再跑一轮；整批失败经 `Result.retry()` 交 WorkManager 退避（进程死亡可续传）。
**影响文件**：parser/pipeline/ParserPipelineImpl.kt、security/SecureHttpClientImpl.kt（429 映射）、domain/error/ReaderError.kt、docs/02 §3/§5.2；二期 data/work/ChapterDownloadWorker.kt。
**风险**：重试放大站点压力与任务时长（预算封顶缓解）；全部为 GET，无幂等性顾虑。
**工作量**：M。

## 3 · 请求频率限制

**现状**：`security/NetworkLimits.kt` 六参数 DEFAULT 硬编码，`di/AppContainer.kt:87` 原样装配；同 host+port 最小间隔 500ms（SecureHttpClientImpl.awaitMinInterval:302-323，可取消挂起）；maxRequestsPerTask=30 由管线计数（客户端不重复计数，契约 §5.2）；并发形态：同书串行（ContentCacheManagerImpl:60-139 同书重复批次取消旧批；prefetch 串行 :141-168），无跨书并发。
**差距**：限流不可按站点定制（慢站 500ms 过快、快站浪费）；无 429 自适应；二期"多书同时批量缓存"的并发策略未定义。
**建议**：
1. 按站点可配置：SourceRule 增可选字段 `requestIntervalMs`（规则 schema v1 增量，缺省回退默认；兼容旧规则导入）；经 FetchRequest 增可选 `minIntervalOverride` 传入，**仅允许调大不允许调小**（限制放大压力的自由度）。
2. 429 学习式退避：SecureHttpClientImpl 内 per-host 内存态退避表——429 后该 host 间隔 ×2（上限如 10s），连续成功后衰减复原；进程内行为不改契约。
3. 并发站点策略：二期 Worker 化后允许跨书并行（每书一条链、书内保持串行），全局并发书数 ≤2；任务名唯一 + KEEP 已由 CacheWorkScheduler:15-24 预置。
**影响文件**：security/NetworkLimits.kt、security/SecureHttpClient.kt（可选参数）、security/SecureHttpClientImpl.kt、data/db/entities/SourceRuleEntity.kt、schemas/source-rule-v1.json、domain/rule/RuleJsonValidator.kt、docs/02 §4.2/§5.3、docs/03 §5。
**风险**：退避表进程重启丢失（可接受）；规则字段扩展需校验器放行缺省；并发放宽对弱站需默认保守。
**工作量**：M。

## 4 · SSRF 防护复核（二期新增攻击面）

**现状结论**：一期矩阵全绿（§0，57/57）；解析级黑名单 + 重定向逐跳复查 + DnsPinningResolver 建连级复核（生产默认参数生效，基线 §9 R-S1）；`allowListForTest` 生产无传值（AppContainer:81 无参构造）。一期攻击面（用户 URL / 站点 HTML）闭环。
**二期新增攻击面复核清单**（各新功能启用前逐条过检）：
1. **WebView 渲染 URL**：`docs/security/审查报告-安全基线.md` §6 六条前置是硬门禁（独立进程、禁文件访问、域名先过 validate、shouldOverrideUrlLoading 逐跳 validateRedirect、最小 JSI、Cookie 隔离）；一期 `DYNAMIC_PAGE_REQUIRED` 是拒绝语义，二期改"渲染取回 HTML"后，采回 DOM **必须**重过 ContentSanitizer 才能入库展示。
2. **TXT/EPUB 导入内嵌链接**：EPUB (X)HTML `<a href>`、TXT 裸 URL 均不可信：① 不做自动预取；外链仅交系统浏览器 ACTION_VIEW 或经 validate 全管线，**不进应用网络层**；② EPUB 内部 zip 资源路径不走网络层，拼接后必须规范化仍在解包根内（zip-slip，同 §8-2）；③ 若立项"EPUB 远端图片"，图片 URL 必须经 SecureHttpClient——**Coil 默认 ImageLoader 无任何 SSRF 校验，直接 `AsyncImage(url)` 加载 http 地址即绕过唯一出口，此为红线**，需写入 docs/01 §2 依赖红线。
3. **备份导入**：详见 §8；与 SSRF 交叉点：备份内书/章节 URL 为不可信输入，恢复时不得触发任何抓取，入库后 refresh/load 仍有管线校验兜底；可导入时预跑 validate 打 `urlBlocked` 标记（新列）供 UI 提示（决策项 §9-3）。
**影响文件**：均为二期新功能面 + security 层复用；红线落点 docs/01-架构方案.md §2。
**风险**：最大实际绕过面是"新功能自带网络出口"（Coil/WebView/第三方 SDK）；纪律：新增出口 = 新增校验点，逐个架构评审。
**工作量**：清单 S；WebView/EPUB 各自执行时各 M。

## 6 · 数据库迁移安全

**现状**：version=1、exportSchema=true、`app/schemas/com.mvxxcb.reader.data.db.AppDatabase/1.json` 实存随仓库；`di/AppContainer.kt:93` 纯 `databaseBuilder().build()`，全仓无 fallbackToDestructiveMigration（复核实证）；`data/db/migrations/` 仅 `.gitkeep` 占位——**MigrationTestHelper 基建未建**（依赖 room-testing 已在 testImplementation；契约 02 §11.5、docs/03 §6-3 均要求迁移必须跑校验）。当前全部 DB 测试走 inMemory，无迁移覆盖。
**v2 候选变更迁移风险清单（安全/完整性红线）**：
1. `reading_progress` 加列：只允许"可空或带默认值"（03 §6.4）；禁止改既有列类型/约束；迁移测试断言进度行数与值恒等。
2. `reading_sessions` 新表：CREATE TABLE 必须与实体逐字段一致（含索引/FK），否则 Room open 抛 validateMigration 错——必须由 `MigrationTestHelper.runMigrationsAndValidate` 兜住；埋点类表写失败 try/catch，不拖垮主流程。
3. SourceRule 扩展：加列同 1；DB 列与规则 JSON schema（schemas/source-rule-v1.json）同步演进，旧规则导入兼容为功能红线。
4. **缓存文件化（content 列 → files 目录 + 路径列）：最高风险项**。文件系统与 DB 无跨介质事务，红线：写文件+fsync → 更新 DB 行 → 清旧列，中途崩溃必须幂等可重跑；建议按书分批（每书一个事务）、可续跑；迁移后逐书复验 contentHash（复用 ContentCacheManagerImpl.verifyBookIntegrity）；过渡期"路径列为空则回读 content 旧列"双读兜底。
5. 通用红线：release 禁 destructive（纪律在案；debug fallback 需显式 WARN）；每个迁移配 MigrationTestHelper 用例（schemas/1.json 为 fixture，断言可打开+行数不变+默认值正确）；万章级大表迁移耗时需量化；备份恢复的旧版本 DB 必须走 Room 正常 open+migration，禁止文件替换旁路（§8-3）。
**影响文件**：data/db/migrations/（新建）、di/AppContainer.kt:93（addMigrations）、app/src/test 新增 MigrationTest、docs/03 §6。
**风险**：缓存文件化迁移失败可致正文丢失（数据完整性红线，双介质过渡必须）；迁移测试缺失时 schema 变更即盲改。
**工作量**：基建 S；各迁移 S；缓存文件化 M-L。

## 7 · 长时间阅读性能

**现状**：章节缓存累积于 chapters.content（预取 radius=1 + 批量缓存；清理入口 clearBookCache/clearAllCaches 已有，ContentCacheManagerImpl:177-195）；Room 默认 WAL（AppContainer:93 未显式设置，Room 2.6.1 默认 WRITE_AHEAD_LOGGING）；Coil 默认 ImageLoader（未自定义缓存上限，ReaderApplication 仅建 AppContainer）；目录 200 条窗口（presentation/catalog/CatalogViewModel.kt:64/190-191，流+本地窗口）；`_pagination` StateFlow 仅持当前章分页，切章即替换；observeChapterMetas 全量收集（万章元数据 ≈ 1-2MB，可接受）；gfxinfo 基线 2.79% jank（万章滚动，验收 §4.1 PERF-01）；分页在 dispatchers.default 且可取消。
**二期风险点与建议**：
1. **数千章全本缓存后**：2000 章 × 均 15KB ≈ 30MB DB；`verifyBookIntegrity` 整表加载全列（ContentCacheManagerImpl:200 经 ChapterDao.getCachedChapters:142 返回含 content 的实体列表）——全本缓存时一次载入数百 MB 有 OOM 风险（当前无 UI 入口，属潜伏缺陷）。建议校验改游标分页或 contentLength 预筛；文件化后改为校验文件哈希。
2. 长会话内存：VM 持有面为当前章+分页+metas 流，events 为无缓冲 SharedFlow 无累积——风险低；建议 debug 构建接 LeakCanary 常驻。
3. 批量缓存写放大：每章一写 + 500ms 间隔天然限速，WAL 默认 checkpoint 够用；避免批缓期间做同步全表扫描。
4. 性能预算与监控点：目录滚动 jank ≤5%（基线 2.79%）；万章 metas 首次发射 ≤500ms；批缓吞吐 ≥1 章/2s（含限流）；DB 体积告警 >200MB（sumContentLength 通道已有，ContentCacheManagerImpl:170-175）；冷启动维持 ≤1500ms。
**影响文件**：data/cache/ContentCacheManagerImpl.kt（校验分页化）、data/db/dao/ChapterDao.kt（游标查询）、可选 ReaderApplication（Coil 缓存上限）。
**风险**：完整性校验在大库上的 OOM 为唯一显性缺陷（未暴露入口前不触发）。
**工作量**：校验分页化 S-M；监控埋点 S。

## 8 · 备份/恢复的安全审查要点（联动 WP-D）

**现状**：`allowBackup="true"` + 双轨规则（res/xml/backup_rules.xml、data_extraction_rules.xml）：Room DB（阅读历史/正文/进度/书签/规则）与 DataStore 纳入云备份/设备迁移，cache/ 排除；基线终审 §6.6 登记 P3（正文大字段或阅读历史建议改 device-transfer-only，WP-M 所有）。
**WP-D 备份方案审查清单（安全侧）**：
1. **文件完整性**：备份文件加 magic 头 + schema 版本字段 + 全文件 SHA-256（复用 data/util/Sha256.kt）；导入先验校验和再解析，校验和不符即拒绝。
2. **路径穿越**：zip 形态的备份，条目名拒绝绝对路径/`..`/符号链接（zip-slip）；解包目标固定 app 内部私有目录；条目数与总大小设显式上限，超限中断并删除半成品。
3. **恶意 DB 风险（最重）**：禁止把用户提供的 DB 文件直接替换为 live 库（crafted schema/trigger/view 风险；替换文件等于放弃 Room 校验位置）。导入流程 = 复制到临时目录 → Room 打开临时副本（迁移与校验发生在副本）→ 经 DAO/Repository 层事务性逐书拷入 live 库 → contentHash 复验 → 删临时副本；备份 schema 版本高于当前 app 拒绝导入并明确报错。
4. **备份内 URL 不可信**：导入过程零网络请求；入库后 refresh/load 有管线校验兜底；可选预跑 validate 打标记（§9-3）。
5. **正文注入面**：恢复 content 必须经 ContentBlockCodec 解码（未知判别字段 `t` 拒该章）并重算 contentHash 比对；禁止原样拼回 JSON。
6. 日志不落完整 URL（01 §8；沿用 SEC-6-1/2 修复模式）；SAF 单文件授权即可，禁 MANAGE_EXTERNAL_STORAGE。
**影响文件**：二期 data/backup/*（WP-D）；复用 Sha256/ContentBlockCodec/verifyBookIntegrity；红线写入 docs/01 §2。
**风险**：恶意备份文件是二期唯一"外部不可信文件直接进应用"新通道；清单 1-3 为硬门禁。
